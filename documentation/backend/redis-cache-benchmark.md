# Redis (Upstash) cache benchmark - #249

Timing comparison across the SAME seeded 60 filter combinations used by the
thorough parity suite (`tests/integration/filtering-sql-thorough.test.ts`,
seed 0x5eed42), replayed against a local dev server through the real HTTP
path (auth + rate limit included) hitting the live Neon warehouse and the
real Upstash database (easy-cobra-105935, run 2026-07-08).

Method: each scenario POSTed to `/api/dashboard/summary` and
`/api/dashboard/facets`.
- "compute" pass: `x-no-cache: 1` header, so the server recomputes from the
  warehouse every time (this also wrote every result to Redis).
- "redis" pass: the dev server was RESTARTED first (empty in-process L1), so
  every request was served by the shared Upstash layer.

## Results (ms per request, 60 scenarios each)

| endpoint | pass | avg | p50 | p95 | min | max |
|---|---|---|---|---|---|---|
| summary | compute | 1540 | 556 | 2397 | 256 | 32964 |
| summary | redis | 377 | 349 | 410 | 322 | 1799 |
| facets | compute | 3107 | 842 | 5077 | 380 | 71696 |
| facets | redis | 409 | 357 | 699 | 322 | 2210 |

- Redis was faster in 58/60 facets scenarios (the 2 exceptions were trivially
  narrow filter states where compute is already fast).
- The tail is where it matters: p95 facets drops 5077ms -> 699ms, and the
  worst cases (broad states like visibility=all, tens of seconds to compute)
  drop to well under a second.
- Both passes share a fixed ~330ms floor of auth + rate-limit round trips to
  Supabase, so the pure cache-vs-compute gap is larger than the totals imply.
- The max values in each pass include the first request after server start
  (Next.js dev compiles the route on first hit); production timings will not
  pay that cost.

Raw per-scenario data: generated by a scratchpad script (bench.mjs) that
reproduces the seeded matrix; per-scenario table below.
